# Turn Action Stub

A widget that drives the current Combatant's turn on `/encounter`. The turn opens with any Afflictions due this Round, then offers the Combatant's actions as buttons grouped under their action-economy category. The stub renders directly below the Encounter Initiative Stub (the Combat Tracker) on the Encounter page and acts on the Acting Combatant (`acting_combatant_id`). Lives in `views/encounter.erb` (action-panel section).

See `ui_conventions.md` for shared rules, `encounter_design.md` for the Combat domain entry points this stub drives, and `encounter_initiative_stub.md` for the tracker it sits beneath.

## Layout

Top to bottom:

1. **Header** — `<Combatant Name>'s Turn` and the Combatant's standing resources (below).
2. **Afflictions due this Round** — one Conditions Save Resolution Stub per due Affliction, shown only when any are due (below). There is no separate "Start of Turn" action: the Combat Pool and Main Actions refill automatically the moment the turn begins (see *Turn start*), so the only start-of-turn interaction is rolling these saves.
3. **Action menu** — the Combatant's actions as buttons grouped under **Main Action**, **Bonus Action**, and **Free Action** headers (the headers reuse the Cast builder's Tier-header font). Each category lists the generic actions that belong to it plus one button per usable **Special Ability** of that category:
   - **Main Action** — `Attack`, `Move`, `Cast`, `Item`, and any `main`-activation Special Ability.
   - **Bonus Action** — any `bonus`-activation Special Ability.
   - **Free Action** — `End Turn`, and any `free`-activation Special Ability.

   An empty category (no generic actions and no Special Abilities) is skipped. A generic action button (styled like a Cast option) opens that action's pane below it; a Special Ability button is handled in place (see *Special*). When the Acting Combatant cannot act (Conditions' *Creature Can Act?* is false — Dying, Dead, or carrying a "cannot act" Active Effect), it is offered no Main/Bonus actions and no Special Abilities — only **End Turn** under Free Action — and the header carries an `(Incapacitated)` suffix.

   **Once an action is picked the category groups collapse** to a single **selected-action row**: the chosen action's name with a **Change** button (re-opens the menu and clears the open action). The row also carries a **confirm slot** on its right: when a rolled **Attack** or **Cast** is ready to apply, its **Commit** button surfaces there — at the top of the stub — so the DM confirms without reaching down to the result. (It mirrors the real Commit button rendered in the result.)

## Header

`<Combatant Name>'s Turn`. The name is resolved via Creatures' *Look up Creature*, falling back to the Combatant's stored `name`, then to `Creature #<id>`. An optional `(<state>)` suffix appears when the Combatant has a salient state — `(Incapacitated)` (Conditions' *Creature Can Act?* is false) or `(Dead)` (Conditions' *Dead?*). Beside it the Combatant's standing resources: **Mana** remaining, **Combat Pool** remaining (`Get Combat Pool − combat_pool_spent`), and **Main Actions** left this turn (`—` before the turn has begun).

## Turn start

When the turn passes to a Combatant — for the first Combatant at *Start Combat*, and for each Combatant the turn advances to on *End Turn* — Combat **automatically** begins that Combatant's turn (`Encounter::State#begin_turn_for`):

- **Refill the Combat Pool.** Combat begins with every Combatant's pool empty (see *Start Combat* in `encounter_design.md`); the pool refills to full at the start of each turn (it is **not** refilled at end of turn).
- **Grant Main Actions.** The Combatant is granted its turn's **two** Main Actions (`MAIN_ACTIONS_PER_TURN`). Spending `Attack`, `Move`, `Cast`, or `Item` decrements the counter. The cap is **not enforced** (the counter may go negative) — it is tracked so the DM can see how many a Combatant has used. The counter is `-1` before a Combatant's first turn.
- **Clear expired Active Effects** for the current Round (Conditions' *Clear Expired Effects*) and **expire** the Combatant's timed spell **Zones**.

This all happens server-side as the turn passes; the DM does not press anything to trigger it.

## Afflictions due this Round

The turn opens with one **Conditions Save Resolution Stub** (`conditions_save_resolution_stub.md`) per Affliction due this Round — the same way the Attack pane mounts the Action Builder; the stub owns none of the save machinery. "Due" means the Affliction's Next Resolution Round has arrived **or** the Affliction is active but has no schedule yet (`next_resolution_round` null — e.g. seeded data or an Affliction inflicted without a clock); the latter is resolved and stamped with a real schedule so a Round-frequency Affliction like `bleeding` then recurs every Round. An Affliction resolves on the afflicted Creature's **next turn**: a Round-frequency Affliction inflicted during combat first ticks this Round when the victim still has a turn coming, or next Round when the victim has already acted (see *Affliction scheduling* in `encounter_design.md`). Each stub is built from a `save` blob (`start_of_turn_saves`) carrying the Creature, the Affliction rule + Potency, the save's Dice Cap and Target Number (the Competency Modifier and the Potency Save Penalty fold into the TN as in *Resolve Affliction*), and a `resolve` reference. The DM rolls the save inside the stub and presses Confirm, which POSTs the net DoIS to `/encounter/resolve_affliction`; the server applies it through Conditions' *Resolve Affliction* (consequence + decay / reschedule) and persists. The Combat Pool / Main Actions have already refilled (see *Turn start*), so there is no finalize step.

## Per-action panes

A generic action button opens its pane below the action menu (the pane is hidden until the button is clicked, and only one is open at a time). Each pane is the action-specific UI.

### Attack

The Attack pane mounts the **Action Builder** (`action_builder_stub.md`) — Combat owns none of the wizard. Combat precomputes the full builder blob server-side (`GET /encounter/attack_builder`) and listens for the builder's `action:confirmed` event, then POSTs the choices to `/encounter/resolve_attack`. The builder walks one decision at a time, each collapsing to a thin `<Label>: <value> [change]` row:

1. **Target** — every other Combatant (body buttons), with a header quick-pick per **enemy** next to the *Target* label: the attacker's enemies are the Combatants on the opposite side of the PC / non-PC line (a Player Character's enemies are the non-PCs, and vice versa). The attack kind (`melee` / `ranged` / `spell`) follows the chosen weapon's category.
2. **Weapon & dice** — each equipped weapon is a row: the weapon name (= largest affordable roll) plus a strip of dice buttons `2…Dice Cap`. The header carries a quick-pick button per weapon that selects it at its **maximum** affordable dice. The Combat Pool cost to roll `n` dice is the flat weapon Speed plus one per die — `Speed + n` (Speed is a flat surcharge, not a per-die multiplier); counts the pool can't afford (`Speed + n > remaining`) are greyed out.
3. **Target's defense** — `No defense`, or a Defensive Action eligible against this attack kind (`encounter_design.md` → *Defensive Actions*): `Dodge` (borrows the **`dex_save`** proficiency for its Dice Cap/Modifiers, any kind), `Block` (Martial, any kind), `Parry` (Martial, **melee only**). All three are **pool-costed** Defensive Actions — the DM picks how many dice (Reaction Action Minimum up to the remaining pool, capped by the Dice Cap). `Dodge` is **not** a Saving Throw and does **not** automatically spend the full Dice Cap. The header carries a quick-pick button per eligible Defensive Action; unlike the weapon quick-picks, these select the **minimum** dice (the Reaction Action Minimum). Because the eligible defenses depend on the chosen target and weapon, these header buttons are choice-dependent (`action_builder_stub.md` → `header_options_map`).
4. **Luck** *(one step per source with Luck to spend)* — before the dice are shown, any source that can spend Luck on this action as a **Reaction** gets its own step: every *other* Combatant holding a Bardic Inspiration Reservoir, plus the **DM** (player id `null`) whenever the DM holds DM Luck. Each step's body is a small table titled with the source's name (a heading above the buttons): one row per **in-play Roll** (the attacker / the defender when a defence was declared — or the caster / target, or the Performer), and up to two columns — **Bardic Inspiration** (a bonus: rerolls low dice) and **Unsettling Words** (a penalty: rerolls high dice). Per Roll the source may spend up to `min(its Luck, that Roll's dice)`. A Bard is offered the Unsettling Words column only when it knows that Talent; the **DM is always offered both** columns (its DM Luck is generic, though the columns keep the Bardic Inspiration / Unsettling Words labels). `No luck` is a header quick-pick (top-right) per step. Picks across all sources are aggregated per Roll into the dice engine's reroll slots — bonuses (and penalties) **do not stack**: only the highest of each sign per Roll takes effect, and each die is rerolled at most once (`dice_resolution_design.md` → *Reroll*). On commit each source is debited by the amount it spent — a Combatant's Bardic Inspiration Reservoir via *Discharge Reservoir*, the DM's pool via its DM Luck (the reroll itself is applied client-side as the DM rolls). The same Luck steps appear on the **Attack**, **Cast**, and channeled-**Performance** flows (any main action requiring dice). DM Luck is generated when a Bardic Inspiration Performance check rolls **negative net Successes**: the inverse is granted to the DM instead of the Reservoir, and DM Luck persists across turns/rounds (it clears only at *End Combat*).

Each option carries a **patch** that mutates the seed Rolls: the Competency + Unaware + Flatfooted Bonus/Penalties fold into each Roll's TN / Starting Value server-side (`DiceResolution.compute_target_number`); picking a target/defense sets the opposing (defender) Roll's name, dice, and TN (Dodge/Parry/Block are all pool-bounded), and `No defense` keeps the defender Roll excluded and restores the attacker's Flatfooted Bonus.

When every step is resolved the embedded **Check Resolution Stub** appears (`Roll All` / `Confirm` + the dice table). The DM rolls (and may reroll/nudge or type a manual override into the Result field), then `Confirm` emits `action:confirmed`. On it, Combat reads each Roll's Successes + the defender dice, and `resolve_attack` recomputes the weapon damage from the chosen weapon, spends Combat Pool per participant, nets Supporting − Opposing Successes per *Check Resolution*, and routes positive net damage through *Apply Damage* → Conditions' *Apply Hit Point Damage* (Temporary HP absorbs worst-first, per `conditions_design.md`).

When the chosen weapon carries magical **Damage Riders** and the hit lands, the rider roll is a **second phase of the same builder**: the rider rows (the rider dice — typically 4 per Property — rolled at the attack's Target Number) render under the collapsed attack results, and the phase's `Roll` / `Confirm` mount into the builder's **top Rolls header** — the same controls slot the attack roll used (never a second mid-panel header). The DM rolls and `Confirm`s; the rows collapse to their own lines (with a Change button) and only then does the editable damage screen appear, now carrying a **separate Damage box per rider** (and a Self-damage box for a rider that bites the wielder) alongside the base Damage / Bleed / Combat-Pool fields + `Commit attack`. Rider bonus damage scores without letting a rolled `1` count against it (`failure_modifier 0`; Crits still double); a `1` only feeds the self-damage. The rolled, DM-editable amounts ride the commit payload as `rider_results: [{ id, damage, self_damage }]`, and each rider applies as its own Severity Calculation. See `encounter_tests.md` → *Magical weapon Damage Riders*.

#### Confirm payload

The shape `Encounter::State#resolve_attack_payload` consumes (symbol or string keys):

- `target_id` — the defender's Combat ID.
- `attack_kind` — `melee` | `ranged` | `spell` (default `melee`).
- `weapon` — `{ damage_types, threshold, base_damage, bleed, affliction }` (optional; falls back to `damage_bonus` + `physical`). `affliction` names a Conditions Affliction the weapon injects on a hit (e.g. a spider's `spider_venom`).
- `override` — `{ damage, bleed, poison, pool_spends }` (commit only). The result preview shows **Damage**, **Bleed**, and — when the weapon carries an `affliction` — a **Poison** input box, each editable before the final Confirm. On commit, positive Damage routes through *Apply Damage*, Bleed and Poison are inflicted through Conditions' affliction channel (Bleed as `bleeding`, Poison as the weapon's `affliction`), scheduled to the victim's next turn. Poison potency defaults to the attack's net Degrees of Success.
- `attacker` — `{ id, dice, speed, successes }`.
- `defense` — `{ choice, id, dice, speed, successes }`. `choice` of `none`/empty skips it; an ineligible defense is rejected before any Combat Pool is spent. Every Defensive Action (Parry / Block / Dodge) costs Combat Pool (`Speed + dice`).
- `allies` — `[ { id, dice, speed, successes }, … ]` for ally Reactions (e.g. a Granted-Action block).

### Move

A Main Action that simply spends the **Move Cost** (`encounter_config.yaml` → `Move Cost`, default 4) in Combat Pool dice — no other mechanical effect. The pane states the cost and a **Confirm Move** button (disabled when the Combat Pool can't afford it); confirming POSTs to `/encounter/move` → `Encounter::State#apply_move`, which spends the dice.

### Cast

1. **Pick spell.** The Combatant's known spells from the character sheet, **grouped by Tier**: a `Tier <n> (<color>)` header (Tier Colors per `ui_conventions.md` — Tier 0 is red) followed by that Tier's spells, skipping any Tier the Combatant has no spell for. Spells the Combatant lacks the Mana for are disabled (per-Tier Mana Cost from `abilities_config.yaml`). The spells are listed without a dice count — dice come next. The list also includes any spell granted by an **equipped Wand or Ring** (`equipment_design.md` → *Item Forms*): a granted spell is cast as if known, channelling the wielder's own Mana, so it appears in the list at its Tier and pays the same Mana Cost. A spell the Combatant already knows is not listed twice.
2. **Pick dice.** Only after a spell is chosen: how many dice to roll on the casting check, bounded by Combat Pool remaining and the spell's casting-skill Dice Cap. Laid out **like the Attack weapon step** — a leading *"&lt;casting skill&gt; (max N)"* quick-pick that selects the maximum affordable dice, then a button per count, with a top-right header quick-pick **named by the casting skill** (e.g. *Arcana*) that selects the maximum. Title-bar quick-picks are always named for the weapon / skill / target they pick — never a bare *"Max"*.
3. **Pick target(s).** A save / defense cannot be rolled without a target, so the target is chosen after the spell and its dice. Driven by the spell's `target` / `area` / `save` fields (`abilities_design.md`).
4. **Roll & defend.** Client-side dice for the spell's casting skill (`skills`, default `arcana`). Spells with a `save:` block prompt the target's Saving Throw (named by the Save Attribute — e.g. a **Wisdom save**); attack-roll spells prompt a Defensive Action (Dodge / Block). A Save spell's Saving Throw always spends the full Dice Cap — the DM is not asked how many dice; the pool-costed Defensive Actions (Dodge / Block) pick their dice.
5. **Submit.** The Spells/Abilities domain resolves the spell's Effects and applies them to the target(s): Mana is debited via Conditions' *Apply Mana Cost*; **magic toxicity** rises via Conditions' *Apply Magic Toxicity* (a positive contribution is blocked when the Combatant's toxicity already exceeds the Toxicity Threshold — `floor(Charisma × Tier)`, with Tier 0 treated as 0.5); cure / heal / Temporary HP / mana / Active-Effect (ward, enhancement) outcomes route to Conditions. Channeled or multi-turn spells register a Concentration or Casting Entry via Encounter (`encounter_design.md` → *Begin Concentration* / *Begin Long Cast*).

### Item

The Item pane **reuses the Cast flow**: a carried consumable casts its Item's spell through the same Action Builder as Cast, so a **Scroll behaves exactly like casting the spell** (same targeting, saves, attack rolls, area placement, and effects) and a **Potion** like casting it on yourself. It reads identically (Spell → Dice → Target → Defense, then a preview → Commit); only the list source and a few resolution inputs differ. The button appears only when the Combatant carries a usable Potion or Scroll.

1. **Pick item.** The Combatant's carried **Potions** and **Scrolls** (Consumable spell-form Items), grouped by Tier like the Cast list — **one button per Item** (you are choosing an *item*, not a skill). The button shows the Item's spell **resolved to the Stack's Tier**, so a multi-Tier spell is never ambiguous: a Tier-1 Potion of Heal reads *Potion of Heal Lesser Wounds*, a Tier-2 one *Potion of Heal Simple Wounds* (a single-Tier spell keeps its plain name, e.g. *Scroll of Fireball*), and the carried quantity shows as *×N* when more than one is held. Each option carries its underlying spell; two Items of the same spell never collide (the option is keyed by the Stack).
2. **Pick dice (and skill).** A consumable offers a choice of casting skill — the spell's own primary skill **and Evocation** (the item-form default), deduped — but rather than ask separately, the skill is **folded into the Dice step**: one Dice row per available skill, each labelled by that skill (*Healing* / *Evocation*), with its own count buttons up to that skill's Dice Cap. Picking a die sets both the dice count and that skill's Competency + the Spell Tier's Inherent Bonus, so it determines how much bleeding a Heal clears (below). Only the **highest-prowess skill's max** is a top-bar quick-pick; the rest live in the rows. A consumable with one usable skill shows a single row (and a no-roll buff auto-applies its known count).
3. **Pick target / defend.** Exactly as Cast. A **Scroll functions exactly as the spell**: it targets like any cast (a single Combatant, or — for an **area** spell — the "Place on the map" footprint whose caught creatures each roll a Save, identical to casting it), and a `save:` / attack-roll prompts the target's Save / Defensive Action. A **Potion** targets the drinker (self): the Target step is **auto-applied** to the Combatant itself and never asked — the stub never poses a question it already knows the answer to. (The same holds in the Cast pane for any Spell that declares `target: self`.)
4. **Commit.** The result block exposes the editable outcomes before committing — including a **heal Effect's per-Severity boxes**: a cure shows one input for each Severity it restores (Minor / Moderate / and, for higher-Tier cures, Major), pre-filled from the spell and adjustable, so the DM sets exactly how much it heals (the same boxes appear for a heal in the Cast pane). A spell whose **channel reduces bleeding** (Heal, `effect_hash.bleed_reduction`) is a **rolled** cast everywhere — drinking a potion or casting it normally rolls the chosen skill, and the casting successes drive the reduction: `floor(spell_tier × 2 × successes)` (Tier 0 counts as 0.5, so Petty Wounds clears 1 bleeding per success) is drained from the target's `bleeding` Affliction Potency via Conditions' *Reduce Affliction Potency* (cleared at 0). The HP cure still applies alongside; the reduction shows in the per-target outcome as `bleeding −N`. On Commit the Cast resolver applies the spell — spending **no Mana** (the Item supplied it), spending Combat Pool (`Speed + dice`), netting against the target's Save / Defense, routing the resolved Effects (cure / heal / Temporary HP / mana / damage / Active Effect) with any edited heal amounts, and dropping an area spell's Zone on the Map. A **Potion** imposes **Item-Form Magic Toxicity** on the drinker (`equipment_design.md` → *Item-Form Toxicity*: `max(Base[Tier] − reducer, Minimum[Tier])`, Source Kind by the spell's polarity); a **Scroll** imposes none. On commit the Consumable's quantity is decremented by one (the Stack is deleted when it hits zero), and a Main Action is spent. A **Wand / Ring** is **not** used here — its spell lives in the Cast list (above) and a Wand is never consumed. (Oils — thrown / applied to *another* target, with target-side toxicity — are not yet wired into this pane.)

### Special

Use one of the Acting Combatant's non-Spell Abilities that does **not** require a Reaction — a Bard's Bardic Performance most prominently, but any qualifying Ability. There is no separate "Special" action: each usable Ability is a button in the action menu, under its own action category (a `main`-activation Ability sits under **Main Action** beside Attack / Move / Cast / Item; a `bonus` one under **Bonus Action**; a `free` one under **Free Action** beside End Turn). Picking one resolves it in place (the result renders just below the action menu).

1. **Usable Abilities.** The Combatant's Granted Abilities filtered to Talents (Spells belong to the Cast pane) that declare an explicit `activation_time` resolving to a non-Reaction action category (`free` / `bonus` / `main`). This admits active Talents (Rage, Turn Undead, Bardic Inspiration) while excluding Reactions (Primal Tenacity, Danger Sense, Better Lucky Than Good), Trigger riders (Sneak Attack, Halfling Luck — a `trigger` and no `activation_time`), and passive / enabler Talents (Trapfinding, Magical Performance, the `*_Spellcasting` feats — no `activation_time`). Each Ability is one button (its name only), placed under the action-menu category matching its activation. A button the Combatant cannot afford is disabled. The button reads the **specific Ability's** name — a Channel Divinity action shows as *Turn Undead* / *Glorious Charge* / etc., never as the *Channel Divinity* category it inherits from (the category has no `activation_time` and is not itself usable). A non-channeled Ability's Confirm summary states both its **Mana cost** and its **Combat-Pool dice** (e.g. *"Spend 1 mana and 4 Combat Pool dice."*) — the Mana is taken from the resolved entry so an inherited Channel Divinity cost surfaces.
2. **Use.** Picking an Ability resolves it. The Ability debits its `mana_cost` via Conditions' *Apply Mana Cost*, and:
   - **Channeled Abilities (Bardic Performance).** Mount the **Action Builder** — the same roll flow as Attack. Bardic Inspiration fills its Reservoir from `check_successes`, so it rolls a real **Performance check** bounded by that skill's **Dice Cap**: the DM picks how many dice to channel from Main Action Minimum up to `min(Performance Dice Cap, Combat Pool Remaining)`. When the Combatant trains **several** Performance skills (`perform_<type>`) the builder first asks **which Performance** to use — its Competency rides the roll and its Dice Cap bounds the dice. (A `channel_dice` / fire channel still runs up to Combat Pool Remaining with no Dice Cap; the cap is also re-checked server-side by the `use_special` route.) The Dice step is shaped **like the Attack weapon step**: it leads with a *"&lt;skill&gt; (max N)"* quick-pick that selects the maximum dice, then a button per count, with a top-right header quick-pick **named by the skill** (e.g. *Perform (Dance)*) that selects the maximum — the same layout the Cast Dice step uses. Confirming the roll does **not** save: the pane then shows how many Luck points the Reservoir will gain (Successes × `fill.ratio`) with a second Confirm button. On that Confirm, Combat spends the channel dice from the Combat Pool and begins the Performance via Encounter's *Begin Concentration* (or continues a running one via *Channel*), adding the Luck to the Reservoir. Discharging the Reservoir is a Reaction handled outside this pane: the Combat page renders a **Bardic Inspiration** panel (DM-only) listing each live Reservoir, where the DM spends Reservoir dice to grant that many Luck Points to any Combatant (`POST /encounter/discharge_inspiration` → `Encounter::State#discharge_luck_reservoir`). Those Luck Points feed the recipient's Attack **Luck** step.
   - **Self-target Abilities with named Effects (e.g. Rage).** Show a summary of the change (e.g. "Spend 1 mana, gain the rage condition.") and a Confirm button — nothing is saved until Confirm. On Confirm, Combat spends the action's **Action Minimum** dice from the Combat Pool (the category's minimum — Free costs none) and applies each unconditional named Effect to the actor through Conditions' *Apply Named Effect* — granting both the Condition (e.g. the `raging` flag) and its Modifiers, whose Formulas (e.g. `1 + level / 3`) Combat resolves against the actor's level — with a duration computed from the Ability's `duration` when it is expressed in turns.
   - **Anything else (e.g. Turn Undead).** Spends the Action Minimum and reports it; the DM resolves targets / Saving Throws manually (those flows are deferred).

Backed server-side by `GET /encounter` (which precomputes the usable list via `Encounter::State#special_options`), `GET /encounter/special_builder` (the Performance-check builder blob), and `POST /encounter/use_special` (`Encounter::State#use_special_payload`).

### End Turn

A single confirm-and-submit button (under **Free Action**) that invokes Encounter's *Advance Turn*, which skips Combatants who cannot act and applies *Apply Per-Turn Cleanup* to the outgoing Combatant — clearing per-Combatant `luck_points`. The outgoing Combatant's Combat Pool is **not** refilled. Advancing then **begins the incoming Combatant's turn** automatically (see *Turn start*): its Combat Pool refills, it is granted its two Main Actions, its expired Effects / Zones clear. A Round wrap additionally triggers *Apply Per-Round Cleanup* and Chronicle's *Advance current Timestamp*.

## Parameters

Required:
- The Acting Combatant (the Combatant identified by `acting_combatant_id`).
- Viewer role — DM only; the stub does not render for players.
- The full Combatant roster (for picking targets).

Optional:
- A combat-log array — the stub appends preview lines as the DM picks values, then commits them on submit.

## Behavior

- Each action pane is client-side until Submit. State accumulates in the browser; only Submit POSTs back.
- Per-Combatant `luck_points` are debited per reroll; a reroll re-rolls a single die client-side. A Save spell's Saving Throw never costs Combat Pool; Defensive Actions (Parry / Block / Dodge) do.
- The Combat Pool is decremented on submit by the action's flat Speed cost plus one per die rolled — `Speed + dice` (the weapon's Speed for Attack; the spell's casting time for Cast). Speed is a flat surcharge, not a per-die multiplier.
- **DM Luck Points** (`dm_luck_points`) are a Combat-level pool shown read-only to the DM; they persist across turns and rounds and clear only at *End Combat*. The Initiative Stub also surfaces this total.

## DM-only

The entire stub is DM-only. The Encounter page is gated by the project's DM identification (a loopback request is the DM; see the project's DM-vs-player rule). The stub renders nothing for player viewers.

## Composition

The stub renders inline on the Encounter page only, directly below the Encounter Initiative Stub, which provides the targeting roster. It is not designed to embed elsewhere.

## First-pass implementation status

The full layout above is the target. It grows as the owning domains and routes land:

- **Implemented:** the panel (`views/_turn_action.erb`, rendered by `views/encounter.erb`; the grouped action menu + pane switching in `public/app.js`, the Attack flow in `public/js/ui/turnAttack.js`).
  - **Turn start (automatic)** — `Encounter::State#begin_turn_for` refills the Combat Pool, grants the Combatant's two Main Actions (`MAIN_ACTIONS_PER_TURN`; tracked on the Combatant as `main_actions_remaining`, default `-1`, decremented by a committed Attack / Move / Cast), runs Per-Turn Setup, and clears expired Active Effects. It runs for the first Combatant when the `POST /encounter/start_combat` route picks the top of initiative, and for each incoming Combatant inside `advance_turn`; both routes also expire that Combatant's timed spell Zones (`begin_turn_side_effects!`). There is no `start_of_turn` route or finalize button.
  - **Afflictions due this Round** — mounts one **Conditions Save Resolution Stub** (`views/_conditions_save_resolution.erb`) per Affliction due (`start_of_turn_saves` → `Encounter::State#pending_afflictions`, which counts an Affliction as due when its Next Resolution Round has arrived **or** when it is active but unscheduled — `next_resolution_round` null, e.g. seeded data). Each `save` blob carries a `resolve` reference, so the stub's Confirm (`public/js/ui/savePreview.js`) POSTs the rolled DoIS to `POST /encounter/resolve_affliction` (`Encounter::State#resolve_affliction_save` → Conditions' *Resolve Affliction*, persisted); without that reference — the Status demo — Confirm stays display-only.
  - **Move** — a Confirm button (under Main Action) that POSTs to `/encounter/move` → `Encounter::State#apply_move`, spending the **Move Cost** in Combat Pool dice and one Main Action.
  - **End Turn** — `POST /encounter/advance_turn` (Encounter's *Advance Turn*), which then begins the incoming Combatant's turn.
  - **Attack** — mounts the shared **Action Builder** (`public/js/ui/actionBuilder.js` + `views/_action_builder.erb`). `GET /encounter/attack_builder` precomputes the blob; `public/js/ui/turnAttack.js` is a thin host that mounts the builder and, on `action:confirmed`, POSTs `/encounter/resolve_attack` (which recomputes the weapon damage server-side, spends Combat Pool, and applies damage). Attacker Bonuses (Flatfooted, Unaware) and Defensive Actions (Parry / Block / Dodge) are assembled server-side into option patches.
  - **Cast** — mounts the same shared **Action Builder** as Attack (`public/js/ui/actionBuilder.js` + `views/_action_builder.erb`). `GET /encounter/cast_builder` precomputes the blob with four steps in order: a **Spell** step (known spells **plus any spell granted by an equipped Wand / Ring** — `granted_spell_items` folds each `grants_spell` Item's spell into the list, deduped against known spells — grouped by Tier — a `Tier <n> (<color>)` header then that Tier's spells, skipping empty Tiers; each Spell shows only its name, its Mana Cost being inferred from its Tier; mana-unaffordable Spells disabled), a **Dice** step (choice-dependent on the spell: a *variable*-count Spell — a rolled cast, or a reservoir pour — lists counts from the spell's **Action Minimum**, Main 4 / Bonus 2, up to the casting skill's Dice Cap, bounded by Combat Pool; a *known*-count Spell — a no-roll buff costs exactly its Action Minimum — is auto-applied with no button, skipping the step), a **Target** step, and a choice-dependent **Defense** step (the target's Saving Throw at full Dice Cap for a Save Spell, Dodge / Block for an attack-roll Spell, nothing for a utility Spell). A Save spell's Saving Throw is **auto-applied** at the full Dice Cap — there is no button, since a Save never picks dice; the pool-costed Defensive Actions (Dodge / Block) pick dice. The caster Roll folds in the casting-skill Competency, the caster's own Tier Inherent, and the Spell Tier as a Guidance Bonus. `public/js/ui/turnCast.js` is a thin host that mounts the builder and, on `action:confirmed`, POSTs `/encounter/resolve_cast`. `Encounter::State#resolve_cast_payload` (with the pure helpers in `Encounter::Cast`) spends Combat Pool (`Speed + dice`), debits Mana, applies **magic toxicity** (gated over threshold), nets the cast against each target's Save or Defensive Action, routes the resolved Effects (damage → *Apply Damage*; heal / mana / Temporary HP / Active Effect → Conditions), and registers a Concentration / Long Cast Entry for a sustained spell. The spell's *Effects* are produced by the Abilities domain (`Abilities.resolve_spell`); the route folds that result onto the payload when present (see *Item* below for the same seam).
  - **Special** — uses a non-Spell, non-Reaction Ability (Bardic Performance et al). `Encounter::Special` classifies the usable Granted Abilities; `Encounter::State#special_options` (precomputed in `GET /encounter`) builds the category-grouped button list. A channeled Performance mounts the shared **Action Builder** (`GET /encounter/special_builder`) so the DM picks the channel dice and rolls the Performance check, exactly like Attack. For a `check_successes` channel (Bardic Inspiration) the dice are a real skill Check, so they run Main Action Minimum → `min(Performance Dice Cap, Combat Pool Remaining)` (`Encounter::Special.check_skills` reads each trained `perform_<type>`'s Dice Cap + Competency); with several trained Performances the builder adds a *Performance* step to pick one. `public/js/ui/turnSpecial.js` POSTs the confirmed dice + Successes to `/encounter/use_special` → `Encounter::State#use_special_payload`, which spends the chosen dice + Mana and begins-or-continues the Performance (Reservoir filled by Successes × `fill.ratio`); the route re-checks the Dice Cap (`channel_dice_cap_error`) before applying. Non-channeled Abilities show a change summary + Confirm and spend the Action Minimum (applying a self Active Effect like Rage). The Reservoir is discharged from the Combat page's DM-only **Bardic Inspiration** panel (`POST /encounter/discharge_inspiration` → `discharge_luck_reservoir`), which spends Reservoir dice and grants Luck Points to the chosen Combatant — surfaced as a tracker badge and consumed by the Attack **Luck** step. Target/Save resolution for offensive Talents (Turn Undead) remains manual.
  - **Item** — reuses the Cast pipeline. `GET /encounter/item_builder` precomputes the **same builder blob** as Cast (`build_cast_blob`), but the Spell list is the actor's carried Potions / Scrolls (`consumable_spell_items` → `consumable_castables`): each casts its Item's spell with the spell's own casting skill (evocation default, `item_cast_skill`), costs **no Mana**, and a Potion / Oil is keyed self-only. The blob carries a `key → Item` map so the host can name the Consumable on the payload. `public/js/ui/turnItem.js` is a thin host (parallel to `turnCast.js`) that mounts the builder and POSTs `/encounter/resolve_cast` with an `item` field. `enrich_cast_payload!` zeroes the Mana Cost and, for a Potion / Oil, computes **Item-Form Magic Toxicity** (`Equipment::Instance#item_form_toxicity`); on commit the route runs `consume_cast_item!` to decrement the charge (Equipment's *Remove Item* + *Cleanup*) and spends a Main Action. Wands / Rings are handled by the Cast list, not here.
